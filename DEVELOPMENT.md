## 2026-08-30 — descriptor and rights foundation

Template and CA searches request `nTSecurityDescriptor` with the LDAP_SERVER_SD_FLAGS_OID control and `DACL_SECURITY_INFORMATION` (0x4), as specified by [MS-ADTS](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-adts/3888c2b7-35b9-45b7-afeb-b772aa932dd0). The native parser decodes self-relative SD headers, ACL order, simple/object ACEs, masks, SIDs, object/inherited-object GUIDs, inheritance flags, and raw ACE bytes. The Enroll extended-right GUID is `0e10c968-78fb-11d2-90d4-00c04f79dc55`, from [Microsoft’s Certificate-Enrollment schema entry](https://learn.microsoft.com/en-us/windows/win32/adschema/r-certificate-enrollment). GenericAll and the enrollment control-access bit are handled; GenericWrite/WriteDacl/WriteOwner are retained as distinct future modification rights and are not treated as enrollment.

LDAP identity collection discovers user/group/computer SIDs and the domain SID. Membership expansion follows `member` links upward through nested groups with a visited set and cache, avoiding cycles. The current low-privilege candidate set is Everyone, Authenticated Users, Domain Users, and Domain Computers; privileged groups are resolved by SID but are not candidates. This is an identity/group approximation, not a full Windows token calculation.

The name flag uses `CT_FLAG_ENROLLEE_SUPPLIES_SUBJECT` (0x1), documented in [MS-CRTD](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-crtd/1192823c-d839-4bc3-9b6b-fa8c53507ae1). Authentication capability accepts Client Authentication (`1.3.6.1.5.5.7.3.2`), Smart Card Logon (`1.3.6.1.4.1.311.20.2.2`), PKINIT Client Authentication (`1.3.6.1.5.2.3.4`), Any Purpose (`2.5.29.37.0`), or no EKU/application-policy restriction. Server Authentication alone is not accepted. Publication is established only through the CA object's `certificateTemplates` relationship; an unpublished template is never reported as direct ESC1.

## MVP implementation

The code separates LDAP collection, models, identity/ACL rights, and pure ESC1 rules. Debug mode exposes decoded flags, EKUs/application policies, ACEs, SIDs, and evidence objects. The rule engine still deliberately requires a CA publication relationship and effective low-privilege enrollment evidence before returning ESC1.

Run unit tests with `python -m pytest` and invoke with `python -m ad_enum --dc-ip 10.1.10.40 --domain SCCM.LAB --username USER` (password is prompted if omitted). No password or lab credential is committed.

Offline LDAP-shaped fixtures A–J are generated by `ad_enum.fixtures.ldap_fixture` and pass through `normalize_directory`, including serialized self-relative `nTSecurityDescriptor` values and CA `certificateTemplates` references. Expected results are A yes, B/C/D/E/F/G/J no, H/I yes. Publication uses case-insensitive CN keys, supports many-to-many CA/template relationships, and reports dangling references and duplicate keys diagnostically.

For object-specific ACEs, `ObjectType` must be absent or equal to the requested right GUID; an unrelated GUID and AutoEnroll do not grant Enroll. `INHERIT_ONLY` ACEs do not apply to the current template. `InheritedObjectType` is decoded and retained; validation against the certificate-template class GUID remains a known limitation because the collector does not yet retrieve/cache that schema class GUID. Unknown ACE types are retained as `unknown` and never grant rights. DACL evaluation is ordered: a deny only blocks rights not already granted by an earlier allow, matching the AD access-check algorithm described by [MS-ADTS](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-adts/c55e113e-25a2-45eb-abba-bf5a9e521a8f).

The prepared, non-executed Enterprise CA procedure is `lab/setup_enterprise_esc1.ps1`. It requires an explicitly authorized Enterprise Admin credential, contains no password, and uses the supported Certificate Templates MMC duplicate-template step followed by `certutil -setcatemplates` publication.
